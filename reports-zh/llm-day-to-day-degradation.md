# 🔥 Claude Code Ops 4.6 分析. 高推理

当 Anthropic 发布 Opus 4.6 这样的模型时，**模型权重** —— 数十亿个学习参数 —— 就被冻结了。训练极其昂贵（数百万美元、数周计算）。没有人会在隔夜重新训练模型。

但权重只是更大系统的其中一层。研究揭示了至少 **7 种不同机制** 可能导致实际的或感知到的质量变化，即使模型权重被冻结。

| 问题 | 答案 |
|----------|--------|
| 模型权重在发布后会改吗？ | **否** —— 所有提供商均确认 |
| 模型日复一日的行为会不同吗？ | **是** —— 已证实 ±8-14% 波动 |
| 这是有意的 "削弱" 吗？ | **否** —— 没有故意降级的据 |
| 基础设施 bug 是真实的吗？ | **是** —— Anthropic 确认了 3 个 bug，影响高达 16% 的请求 |
| 有些是心理原因吗？ | **是** —— 确认偏差和蜜月效应是真实的 |
| 系统提示/后训练会变化吗？ | **是** —— 各提供商均有记录 |
| 用户应该相信他们的感知吗？ | **部分地** —— 实际原因存在，但感知会放大它们 |

## 完整推理栈

模型权重是冻结的，但它们之上还有**九个层**可以各自影响你的体验：

```
┌──────────────────────────────────────────────┐
│  你的会话上下文                               │  ← 会话内退化
│  （累积错误、长对话）                          │
├──────────────────────────────────────────────┤
│  系统提示                                     │  ← 定期更新
│  （安全规则、行为指令）                        │
├──────────────────────────────────────────────┤
│  后训练（RLHF / 微调）                        │  ← 可以静默更新
│  （指令遵循、安全对齐）                        │
├──────────────────────────────────────────────┤
│  采样参数                                   │  ← 服务器端可调
│  （温度、top-p、top-k）                       │
├──────────────────────────────────────────────┤
│  投机解码                                   │  ← 草稿模型质量变化
│  （草稿模型预测 + 验证）                       │
├──────────────────────────────────────────────┤
│  MoE 路由 / 批处理组成                        │  ← 已证实 ±8-14% 波动
│  （每个请求激活哪些专家）                      │
├──────────────────────────────────────────────┤
│  硬件路由                                   │  ← TPU vs GPU vs Trainium
│  （哪个集群服务你的请求）                      │
├──────────────────────────────────────────────┤
│  量化级别                                   │  ← 负载下可能变化
│  （FP16 vs INT8 vs INT4 精度）                │
├──────────────────────────────────────────────┤
│  编译器和运行时                              │  ← 已证实 XLA bug
│  （XLA:TPU, CUDA, 特定硬件代码）               │
├──────────────────────────────────────────────┤
│  模型权重（冻结的）                            │  ← 这些不会变化
│  （数十亿学习参数）                            │
└──────────────────────────────────────────────┘
```

核心心智模型：**冻结权重 ≠ 冻结行为**。这就像说 "相同引擎 = 相同驾驶体验"，却忽略了轮胎、路况、燃油质量和驾驶者疲劳。

## 已证实的原因：基础设施 Bug

### Anthropic 2025 年 9 月的事后分析

2025 年 9 月，Anthropic 发布了一份详细的事后分析，揭露了 **三个单独的基础设施 bug**，导致 2025 年 8 月至 9 月间 Claude 的质量退化。他们的官方声明：

> "我们不会因需求、一天中的时段或服务器负载而降低模型质量。用户报告的问题完全是由基础设施 bug 所导致的。"

### Bug #1 —— 上下文窗口路由错误

Sonnet 4 请求被意外路由到配置为 1M 令牌上下文窗口的服务器，而非标准服务器。

- **时间线**：8 月 5 日引入，8 月 29 日负载均衡变化后恶化
- **峰值影响**：最严重时段（8 月 31 日）16% 的 Sonnet 4 请求受影响
- **用户影响**：约 30% 的 Claude Code 用户至少有 1 条退化消息
- **阴险细节**：路由是 "粘性" 的 —— 一旦你命中坏服务器，后续请求将继续去那里
- **已修复**：9 月 4-18 日（跨平台逐步推出）

### Bug #2 —— TPU 输出损坏

TPU 服务器的配置错误导致令牌生成过程中出现错误，给本应极少出现的令牌分配了高概率。

- **症状**：英文回复中间突然冒出泰语或中文字符，明显的代码语法错误
- **受影响**：Opus 4.1 和 Opus 4（8 月 25-28 日），Sonnet 4（8 月 25 日-9 月 2 日）
- **范围**：仅 Claude API；第三方平台不受影响
- **已修复**：9 月 2 日回滚

### Bug #3 —— XLA:TPU 编译器错误编译（最恶心的一个）

修复精度问题的代码更改意外暴露了 Google XLA:TPU 中一个**潜在的编译器 bug**。

- **根本原因**：近似 top-k 操作（用于选择最可能的下一个令牌）"有时返回完全错误的结果，但仅针对特定的批处理大小和模型配置"
- **为什么难以发现**：它的行为取决于在其之前或之后运行的操作，以及是否启用了调试工具
- **隐藏了数月**：2024 年 12 月之前的一个工作方案意外地掩盖了这个更深层的 bug
- **受影响**：已确认 Haiku 3.5；Suspected Sonnet 4 和 Opus 3 的子集
- **解决方案**：从近似 top-k 切换到精确 top-k；接受 "轻微效率影响"，因为 "模型质量是不可妥协的"

### 为什么检测如此困难

Anthropic 自己的自动化评估没有捕获用户报告的退化，"部分原因是 Claude 经常能从孤立的错误中恢复得很好。" 每个 bug 在不同的平台上以不同的速率产生不同的症状，导致"混乱的报告混合，无法指向单一原因"。

关键上下文：Claude 运行在**三个不同的硬件平台**上（AWS Trainium、NVIDIA GPU、Google TPU），每个都有不同的故障模式、编译器和精度行为。你的请求可能在不同天命中不同的硬件。

## 已证实的原因：MoE 路由方差

现代大型模型通常使用**混合专家（MoE）架构**，其中只有模型参数的子集（"专家"）对每个输入激活。一个学习的路由器决定使用哪些专家。

Scale AI 的研究揭示了一个关键发现：

> "稀疏 MoE 和批处理推理的组合产生了不可预测的结果，因为批处理的组成可以决定你的查询被路由到哪个专家，而同一批中来自其他用户的查询混合是不确定的。"

### 各提供商间测得的日间方差

| 提供商 | 日间评分方差 |
|----------|--------------------------|
| OpenAI（GPT-4 变体） | ±10–12% |
| Anthropic（Claude 变体） | ±8–11% |
| Google（Gemini 变体） | ±9–14% |

具体示例：同一模型在**一天的越狱抵抗力为 77%，次日降至 63%**。相同模型、相同权重、相同测试 —— 仅来自基础设施的 14 个百分点波动。

这意味着即使零 bug 且零变化，同一模型仅因请求批处理和路由方式的不同，在不同天产生质量明显不同的输出。当日间噪声为 10-15% 时，A/B 测试无法可靠地检测 5% 的质量信号。

## 已证实的原因：系统提示和后训练更新

### 系统提示变化

模型权重没有变化，但**系统提示**（包裹这些权重）可以随时更新。对 Claude 系统提示演变的分析显示了数十次迭代，"热修复" —— 为修补不需要行为而添加的短指令 —— 被定期添加和移除。

Claude 3.7 的系统提示包含多个针对常见 LLM "陷阱" 的热修复指令。Claude 4.0 的系统提示移除了所有这些，改为在通过强化学习的后训练期间解决这些行为。

### 后训练理论

对于未解释的质量变化，最合理的理论是公司可以更新**微调和 RLHF**（来自人类反馈的强化学习），而不改变基础模型权重。这在技术上使得 "模型没有变化" 的说法是真实的，同时仍然通过更新的安全护栏和指令遵循调整来改变行为。

## 已证实的原因：静默模型替换

OpenAI 已被证实多次静默更改用户交互的模型：

- 隔夜移除模型选择器，强制用户从 GPT-4o 切换到 GPT-5
- 将 GPT-4o 设为隐藏的 "遗留模型"，需要在设置中手动切换，应用内无通知
- "自动切换器" bug 将用户路由到错误的模型
- Plus 订阅者报告模型在未经同意情况下切换到 "受限版本"

Sam Altman 承认发布 "比我们希望的更颠簸"。Reddit 帖子收到了数千个赞，称新模型是 "灾难" 和 "降级"。

这表明模型替换**确实发生在行业中** —— 有时是有意的（产品决策），有时是意外的（路由 bug）。

## 促成因素

### 负载下的量化

为了经济高效地服务数百万用户，公司可能提供模型的**量化**版本 —— 将精度从 FP16 降低到 INT8 或 INT4。这可以将内存使用减少 2-4 倍并加速推理，但引入了微妙的质量损失。提供商是否在负载下动态切换量化级别尚存争议，但 vLLM 和 TensorRT 等服务框架中的技术能力是有据可查的。

### 投机解码

现代服务栈使用较小的 "草稿" 模型预先预测多个令牌，然后让真正的模型验证它们。理论上这保留了相同的输出分布，但实际上接受率因领域和上下文而异。开箱即用的草稿模型在某些情况下可以正常工作，但在特定领域任务或非常长的上下文中经常遇到困难。

### 上下文窗口污染

在长时间的编码会话中，早期错误会累积在上下文中。模型看到自己的错误并可能延续它们。这是单次会话中 "Claude 变笨" 的最常见原因 —— 这不是模型退化，而是上下文污染。

**实用提示**：当感觉质量不佳时使用 `/compact` 或开启新会话。这是你可以做的最有操作性的事情。

## 斯坦佛研究 —— 以及为什么它很复杂

斯坦佛大学和加州大学伯克利分校的标志性 2023 年研究（Chen, Zaharia, Zou）—— *"ChatGPT 的行为如何随时间变化？"* —— 经常被引作为 LLM 退化的证明。标题发现：

> GPT-4 在 "判断这个数是否是质数？一步步思考" 上的准确率从 3 月的 **97.6%** 降至 6 月的 **2.4%**。

### 研究证明了什么

- "相同" LLM 服务的行为**可以在短期内大幅变化**
- 不同的能力可以反方向移动（GPT-4 数学变差，GPT-3.5 变好）
- 代码生成质量下降（GPT-4 可执行代码：52% → 10%）
- 研究创造了术语 **"LLM 漂移"**

### 方法论批评

- 三月版使用**温度 0.0**，而六月版使用**温度 1.0** —— 一个增加随机性的根本性混淆变量
- 每个任务仅有 **500 个查询** —— 对于决定性统计声明来说太小
- "数学问题" 实际上是模型猜测模式变化的是非题，而非数学能力
- 变化可能反映的是有意的**后训练安全更新**，而非退化

研究证明了一件重要的事 —— LLM 行为随时间变化 —— 但机制很可能是有意更新，而非无意退化。

## 心理学

### 确认偏差

一旦有人发推 "Claude 今天变笨了"，你就开始注意到每一个错误。在没人抱怨的日子里，你会忽略同样的错误。社交媒体放大了这种效应。

### 蜜月效应

用户对新模型有一个初始的蜜月期，然后逐渐发现局限性。模型没有变化 —— 期望上升的速度超过了能力。

### 任务难度方差

你的任务日复一日地变化。一天困难的问题感觉像模型变差了，即使它并没有。

### "周末 Claude" 神话

尽管许多用户相信一周内某天有质量模式，但严格分析发现**没有一致的证据**支持一周中某天的质量模式。一个名为 "AI 在周一更笨" 的分析一无所获。

### LLM 的随机性质

LLM 是概率性的。同一提示每次可以产生不同的输出。在运气不好的时候，你可能连续收到几个差的回复 —— 纯随机性，而非退化。

## 总结

用户描述的现象**是真实的，但归因错误**：

- **正确**：他们在某些日子的体验退化了
- **错误**：模型被有意 "削弱" 了

实际原因是以下组合：

1. **基础设施 bug** —— Anthropic 事后分析已证实（高达 16% 的请求受影响）
2. **MoE 路由方差** —— Scale AI 测得 ±8-14% 质量波动，即使零变化
3. **系统提示和后训练更新** —— 各提供商均有记录
4. **硬件异质性** —— TPU vs GPU vs Trainium，各有不同的故障模式
5. **上下文污染** —— 长会话降低会话质量
6. **确认偏差** —— 社交媒体放大感知模式
7. **随机方差** —— 同一模型、同一提示、每次输出不同

测量问题严重：日间 ±8-14% 的波动意味着你无法区分真正的 5% 质量变化和噪声。这就是为什么 "都是你想象" 和 "他们削弱了它" 两方都感到自信 —— 信噪比使得仅凭个人经验无法判断。

# 🔥 Codex 5.3 高推理和发现

### 报告范围

本节解释为什么用户可能会经历一个短暂的窗口期，其中 Claude 输出质量下降，而 Codex 5.3 在实际服务条件下的编码任务中感觉稳定或更强。重点不是永久的模型质量排名。重点是真实服务条件下的短期生产行为。

报告日期：2026 年 3 月 5 日。

### 观察到的模式

报告的模式是：

1. 模型质量在一个时期内可以接受。
2. 质量在几天内似乎退化。
3. 质量回归到接近先前基线。

这种形状通常是服务栈或发布模式，而不是永久基础模型能力变化。永久能力下降通常不会在没有显式回滚或修复的情况下这么快恢复。

### 高推理：为什么 Codex 5.3 在退化窗口中看起来更好

Codex 5.3 可以在另一个提供商的退化期间明显感觉更强，有几个可以同时发生的技术原因：

1. **产品目标匹配。** Codex 5.3 针对代码生成和 agent 编码工作流进行了优化，因此即使原始模型强度相等，由于工具编排、仓库推理和面向代码的指令调优，也能产生更好的编码结果。
2. **推理策略差异。** 各提供商独立调整延迟、推理深度和解码默认值。一个提供商的保守策略在当天可能看起来比另一个提供商的激进速度优化策略 "更聪明"。
3. **服务路径分离**。即使两个提供商都托管最先进的模型，它们运行不同的路由层、编译器/运行时堆栈和发布管线。一个堆栈中的事件并不意味着另一个堆栈中的相关退化。
4. **发布和回滚时间**。如果一个提供商正在发布中而另一个稳定运行，用户可以看到大的临时质量分歧，而没有背后的模型权重的长期变化。
5. **会话级污染效应**。在长的编码对话中，错误积累可以放大感知下降。竞争对手的助手感觉更好，仅仅是因为失败的会话被重置了，或者其工具循环恢复得更快。

### 详细发现

对于像 "Claude 感觉非常弱大约四天，然后回来了" 这样的报告，最可能的解释是：

1. 提供商端的事件、路由问题、解码/运行时 bug 或发布回归影响了部分请求。
2. 问题持续足够长的时间，以便在真实工作流中被反复注意到。
3. 问题被修复或回滚。
4. 感知质量快速恢复。

在同一时期，Codex 5.3 可能感觉明显更好，因为它没有共享相同的事件路径，而且编码任务优化放大了实际结果的差距。

### 假设排序对于这种模式

| 假设 | 可能性 | 理由 |
|------------|------------|-----------|
| 提供商事件加上回滚 | 高 | 最匹配多天下跌然后快速恢复 |
| 服务配置变化（采样/延迟/推理预算） | 高 | 常见的突然行为变化源，无需模型重训练 |
| 静默别名或快照移动 | 中-高 | 可以在没有明显用户行动的情况下改变行为 |
| 提示漂移和上下文污染仅限 | 中 | 可以退化会话，但不太可能单独解释广泛的多天报告 |
| 永久基础模型退化 | 低 | 与快速返回先前质量不一致 |

### 什么可以证实或证伪这个发现

要将此从高置信度推断变为硬证明，请为同一组任务跨天收集请求级遥测数据：

1. 请求时的确切模型标识符和快照/别名。
2. 提供商暴露的任何后端指纹或发布标记。
3. 解码参数（温度、top_p、top_k、最大令牌）。
4. 延迟、超时和错误率追踪。
5. 固定编码基准提示集上的结构化质量评分。
6. 失败点的会话长度和令牌上下文深度。

如果质量下降与事件窗口、配置变化或后端指纹偏移相关，则事件/配置假设被证实。如果没有此类偏移且退化仅在长会话中，上下文污染成为主要解释。

### 实际工程指南

减少生产中的日间方差：

1. 尽可能固定模型快照，而非使用浮动别名。
2. 存储请求元数据（模型 ID、参数、延迟、错误、响应质量标签）。
3. 为编码任务运行固定的每日金丝雀套件并对回归发出警报。
4. 在多次失败回合后重置或压缩长运行会话。
5. 保留回退提供商/模型路径以备事件窗口。
6. 在内部仪表板中将 "模型质量" 与 "服务可靠性" 分开。

### 最终结论

Codex 5.3 在短暂 Claude 退化窗口中看起来更好是一个技术上合理且可预期的结果，在现代 LLM 运营中。最强的解释不是永久模型崩溃。最强的解释是一个提供商的临时服务路径退化，加上另一个提供商在相同周期内特定于编码的优化和稳定运行。
